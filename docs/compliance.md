# Compliance and safety controls

These controls must be reviewed by a lawyer against current Indian telecom and
data-protection rules before any real customer campaign. This document describes what the
code enforces as of Milestone 1; it is not legal advice.

## 1. Consent first

- `consents` stores one record per contact + channel (`voice`, `email`) with `granted` or
  `revoked`, free-text proof, and `recorded_at`.
- `check_channel_allowed()` blocks any send unless a granted consent exists (or a caller
  explicitly supplies a documented lawful basis, which the voice module must record).
- Contact eligibility is exposed at `GET /contacts/{id}/eligibility` so the dashboard and
  every worker use the same gate.
- Bulk import does **not** imply consent. Imported contacts must have consent recorded before
  a campaign can contact them.

## 2. DND and suppression

- `suppressions` is checked before every send, by normalized phone/email per channel.
- Reasons: `dnd`, `unsubscribe`, `bounce`, `complaint`, `manual`.
- Suppressions are permanent in Phase 1: the API exposes create/list/delete, but product
  flows only add them. Re-enabling a suppressed address requires an explicit owner action.
- Unsubscribe, bounce and complaint handlers (Milestones 2/4) must write a suppression in
  the same transaction as the event.
- National DND registry integration is **not implemented**. Until a registry provider is
  selected, DND entries are added manually/imported and the absence of a registry check is
  logged; it is never treated as a clean result.

## 3. Calling hours

- Workspace `settings.calling_hours` defaults to `09:00-21:00` local time
  (`DEFAULT_CALLING_WINDOW`).
- The voice dialer (Milestone 4b) must evaluate the contact's timezone before dialing and
  skip out-of-window contacts with a logged reason.
- The legal window still needs confirmation (open question in `architecture.md`).

## 4. Number series

- The correct Vobiz series (140 promotional, 1600 transactional/service, 92) and DLT
  registration depend on the customer and use case. This is a configuration/deployment
  decision, not a code default. Do not launch outbound calling until confirmed.

## 5. AI disclosure

- Voice agent prompts must open by identifying the business and stating that the caller is
  an automated assistant, and must answer honestly when asked if it is a person.
- The voice agent configuration (Milestone 4) will require an opening line containing this
  disclosure; validation is planned with the agent config.
- Email content generated by AI is visible and editable before sending (Milestone 2).

## 6. Recording and transcripts

- Consent to record/transcribe must be captured in the call flow; refusal stops recording.
- `call_turns` stores transcripts for the dashboard. A retention period and delete-on-request
  path still need a legal decision. Until then, do not enable recording for real campaigns.
- The API never logs full phone numbers, emails or API keys. Structured logs include IDs and
  status codes only.

## 7. Human handoff

- Voice outcomes include `handoff`; the agent must end politely when the contact is upset,
  asks for a human, or the agent is unsure. The transcript and outcome are stored.

## 8. No false claims

- Agents may state only facts in the campaign brief/knowledge provided. Prompts must forbid
  inventing prices, results, availability or legal outcomes. SEO and email prompts follow
  the same rule.
- AI recommendations in the SEO module must cite the pages/issues they are based on.

## 9. Personal data

- Secrets come only from environment variables; `.env` is gitignored and CI fails if a
  `.env` file is committed.
- Passwords use Argon2id. Tokens are short-lived (15 min access, 7 days refresh).
- API logs deliberately avoid payload dumps. Request IDs are used for tracing.
- Export/deletion of a contact's data: contact delete removes its dependent rows (cascade).
  A full export endpoint is planned for the hardening milestone.
- Webhook payloads are stored raw for audit; restrict database access accordingly.

## 10. Site safety

- SEO audits are read-only. Crawling is limited to verified sites, respects `robots.txt`,
  uses a page/depth limit and a polite rate. The crawler never logs in, submits forms or
  changes a customer site.
